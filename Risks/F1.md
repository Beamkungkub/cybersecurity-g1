# F1 – Payslip Workflow Combining External Access, Identifier-Bearing URLs and Unhandled Server Errors Resulting in Compounded Exposure of Payroll Data

**Series:** F
**Likelihood × Impact:** L 3 × I 3 = R 9 🟡 Medium
**Evidence Confidence:** Medium
**Affected Asset / System:** ORG1-APP1 – workflow StaffSalary → RepSlip (ใบจ่ายเงินเดือน)
**Target / Environment:** -
**Analysis Date:** 2026-11-26
**Log Range:** 2025-11-19 00:00:00 – 2025-11-28 23:50:00
**Evidence Sources:** `u_ex251119.log` – `u_ex251128.log`, `result_v3.txt` (หัวข้อ C, D, G), รายงาน D1 และ D2

## Risk Statement

เนื่องจากหน้าใบจ่ายเงินเดือน (RepSlip) ถูกเรียกต่อจากหน้า StaffSalary โดยส่งตัวระบุผ่าน GET query, ถูกใช้จากทั้ง IP ภายในและภายนอก และมีบางคำขอที่ตอบกลับด้วยข้อผิดพลาด HTTP 500 อาจทำให้ปัญหาแต่ละด้านเสริมกันจนเกิดช่องทางรั่วไหลของข้อมูลเงินเดือน (เช่น จากหน้าแสดงข้อผิดพลาดหรือการจัดการข้อผิดพลาดที่ไม่เหมาะสม) ส่งผลให้ความลับของข้อมูลเงินเดือนมีความเสี่ยงเพิ่มขึ้น

## เหตุผลการให้คะแนน

- **Likelihood 3:** พบหลักฐานจากหลายมิติใน workflow เดียวกัน แต่เหตุการณ์ 500 มีเพียง 3 ครั้งในวันเดียว และไม่พบหลักฐานว่ามีการรั่วไหลจริง
- **Impact 3:** กระทบ workflow ใบจ่ายเงินเดือนเป็นหลัก (ข้อมูลส่วนบุคคลอ่อนไหว) แต่ขอบเขตจำกัดอยู่ที่หน้าเดียว
- **Risk Level:** Medium (9) – ปัจจัยหลายอย่างซ้อนกัน แต่ความถี่ของข้อผิดพลาดต่ำและยังไม่เห็นผลกระทบจริง

## หมวดหมู่ความเสี่ยง

- **Primary Category:** Correlation Issues
  - รวมหลักฐานจากหลายมิติ (referer, ที่มาของผู้ใช้, พารามิเตอร์, status) ใน workflow เดียว
- **Secondary Categories:**
  - **Information Disclosure & Technical Exposure Risk:** ตัวระบุใน URL/Referer และหน้า error
  - **Insecure Application Configuration:** การจัดการข้อผิดพลาดบนหน้าเงินเดือน

## หลักฐาน

### E-01 – RepSlip ถูกเรียกต่อจาก StaffSalary และใช้ GET พร้อมตัวระบุ

**Source:** `u_ex251119.log` – `u_ex251128.log` (ฟิลด์ `cs(Referer)`, `cs-uri-query`), `result_v3.txt` หัวข้อ C
**Timestamp:** 2025-11-19 – 2025-11-28

**Observed Facts:**
- RepSlip 85 request: Referer เป็น `StaffSalary.aspx` 83 ครั้ง และ `StaffInfo.aspx` 2 ครั้ง
- ทั้ง 85 request เป็น GET พร้อมพารามิเตอร์ `id`, `periodid`, `salarytype` และ Referer พกพารามิเตอร์ `id` มาด้วยทั้ง 85 ครั้ง

**Security Interpretations:**
- เป็นเส้นทางใช้งานปกติ: เลือกพนักงาน/งวดจากหน้าเงินเดือน แล้วเปิดใบจ่ายเงินเดือน
- ตัวระบุจึงอยู่ใน log ทั้งสองฟิลด์ตลอด workflow (ดูรายงาน D1)

### E-02 – RepSlip ใช้จากทั้งภายในและภายนอก

**Source:** `result_v3.txt` หัวข้อ C และ D (สรุปจาก log)
**Timestamp:** 2025-11-19 – 2025-11-28

**Observed Facts:**
- RepSlip จากภายนอก 27 request (13 IP, 11 ผู้ใช้) และพบในเก้าวันจากสิบวัน
- จากภายนอก: status 200 จำนวน 26 และ 500 จำนวน 1

**Security Interpretations:**
- ข้อมูลใบจ่ายเงินเดือนถูกเรียกผ่านอินเทอร์เน็ตเป็นประจำ (ดูรายงาน D2)
- ไม่ทราบว่าผู้ใช้เหล่านี้ใช้ผ่าน VPN หรือไม่

### E-03 – HTTP 500 บน RepSlip ในวันเดียวกัน ขนาดตอบกลับเท่ากัน

**Source:** `u_ex251127.log` (ฟิลด์ `sc-status`, `sc-bytes`, `cs-username`), `result_v3.txt` หัวข้อ G
**Timestamp:** 2025-11-27 03:03:30, 03:03:33, 05:40:24

**Observed Facts:**
- พบ 500 บน RepSlip 3 ครั้ง ทั้งหมดในวันที่ 2025-11-27: สองครั้งจาก IP ภายในเดียวกันห่างกัน 3 วินาที และหนึ่งครั้งจาก IP ภายนอก
- ทั้งสามครั้งมี Referer เป็น `StaffSalary.aspx` และขนาดตอบกลับเท่ากันที่ 5,829 ไบต์
- 2 ใน 3 ครั้งไม่มี username ใน log (`-`)
- ในชุด log มี 5xx ทั้งหมด 7 ครั้ง (RepSlip 3, login 2, DXXRDV.axd 2)

**Security Interpretations:**
- ขนาดเท่ากันสอดคล้องกับหน้าข้อผิดพลาดเดียวกัน แต่ไม่ทราบเนื้อหาว่าเป็นหน้าทั่วไปหรือรายละเอียดทางเทคนิค
- ข้อผิดพลาดกระจุกในวันเดียวและ workflow เดียว จึงอาจเกี่ยวกับข้อมูลหรือพารามิเตอร์เฉพาะช่วงนั้น แต่สรุปสาเหตุไม่ได้

## การวิเคราะห์ช่องโหว่และความเสี่ยง

1. **Compounded Exposure on Payslip Workflow:**
   - **Evidence:** E-01, E-02
   - **Analysis:** workflow เดียวมีทั้งตัวระบุใน URL/Referer และการเข้าถึงจากภายนอก
   - **Potential Impact:** ปัจจัยที่ซ้อนกันเพิ่มโอกาสให้ข้อมูลเงินเดือนถูกเปิดเผยหากเกิดช่องโหว่อื่นร่วมด้วย
   - **Limitation:** แต่ละปัจจัยเป็นความเสี่ยงอ้อม ไม่ได้ยืนยันการรั่วไหลจริง

2. **Error Handling on the Payslip Endpoint:**
   - **Evidence:** E-03
   - **Analysis:** RepSlip ตอบ 500 ซ้ำในวันเดียว โดยบางครั้งไม่มี username ใน log
   - **Potential Impact:** หน้า error ที่ไม่ได้ปรับแต่งอาจเปิดเผยข้อมูลทางเทคนิค หรือบ่งชี้การรับพารามิเตอร์ที่ไม่ถูกต้อง
   - **Limitation:** ไม่มี response body และไม่มี application log

## ข้อแนะนำ

### Immediate / Short-term (Quick Win)

1. **ตรวจสอบสาเหตุของ 500 บน RepSlip เมื่อวันที่ 2025-11-27 และเปิดใช้ Custom Error Page**
   - **Priority:** Medium
   - **Owner:** Application Development / IIS Admin
   - **Estimated Effort:** Low
   - **Verification:** ทดสอบส่งพารามิเตอร์ผิดแล้วได้หน้า error ทั่วไปที่ไม่แสดงรายละเอียดทางเทคนิค
2. **ตั้งการแจ้งเตือนเมื่อ 5xx ซ้ำบนหน้าเงินเดือน**
   - **Priority:** Medium
   - **Owner:** Infrastructure / SOC
   - **Estimated Effort:** Low
   - **Verification:** จำลอง 500 สองครั้งแล้วต้องมี alert

### Long-term / Architectural Fix

1. **ออกแบบ workflow ใบจ่ายเงินเดือนให้ไม่ส่งตัวระบุผ่าน GET และตรวจสิทธิ์ทุก request**
   - **Priority:** High
   - **Owner:** Application Development + Security
   - **Estimated Effort:** High
   - **Verification:** ทดสอบเจาะระบบและตรวจ log ว่าไม่พบ `id` ใน `cs-uri-query` และ `cs(Referer)`
