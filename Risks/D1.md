# D1 – Sensitive Payroll and Personnel Identifiers Passed via GET Query Strings Resulting in Identifier Exposure Through Access Logs

**Series:** D
**Likelihood × Impact:** L 4 × I 3 = R 12 🟠 High
**Evidence Confidence:** Medium
**Affected Asset / System:** ORG1-APP1 – โมดูล MIS/Staff (RepSlip, StaffSalary, StaffInfo, Web025_1, StaffAttRequestData)
**Target / Environment:** -
**Analysis Date:** 2026-11-26
**Log Range:** 2025-11-19 00:00:00 – 2025-11-28 23:50:00
**Evidence Sources:** `u_ex251119.log` – `u_ex251128.log` (ประมวลผลด้วย `evidence/analyze_v2.py`, `evidence/analyze_v3.py`), `result_v2.txt`, `result_v3.txt`, `README.txt`

## Risk Statement

เนื่องจากหน้าที่เกี่ยวกับเงินเดือน ใบจ่ายเงินเดือน และข้อมูลบุคลากรส่งตัวระบุ (`id`, `periodid`, `salarytype`) ผ่าน HTTP GET query string และ IIS บันทึกฟิลด์ `cs-uri-query` อาจทำให้ตัวระบุดังกล่าวปรากฏใน access log และบริบทอื่นที่เก็บ URL (เช่น browser history หรือ proxy log) ส่งผลให้ความมั่นคงปลอดภัยของข้อมูลส่วนบุคคลลดลง และเพิ่มความเสี่ยงต่อการเข้าถึงข้อมูลโดยไม่ได้รับอนุญาตหากการควบคุมสิทธิ์ระดับออบเจกต์ไม่เพียงพอ

## เหตุผลการให้คะแนน

- **Likelihood 4:** พฤติกรรมเกิดสม่ำเสมอในหลายหน้าตลอดช่วง log (RepSlip 85/85 request เป็น GET ที่มี query และ Referer พก `id` ตามมาด้วย) แต่ยังไม่พบเหตุการณ์ที่ตัวระบุถูกนำไปใช้โดยมิชอบ จึงไม่ให้ 5
- **Impact 3:** กระทบหลาย workflow ของงานบุคคล/เงินเดือน แต่ตัวระบุเองยังไม่ใช่ข้อมูลส่วนบุคคลเต็มรูปแบบ และไม่พบหลักฐานการไล่ค่า id จึงให้ 3
- **Risk Level:** High (12) – พฤติกรรมต่อเนื่องและผูกกับข้อมูลบุคลากร แต่หลักฐานยังไม่แสดงการนำไปใช้โดยมิชอบ

## หมวดหมู่ความเสี่ยง

- **Primary Category:** Information Disclosure & Technical Exposure Risk
  - ตัวระบุของข้อมูลเงินเดือน/บุคลากรอยู่ใน URL ที่ถูกบันทึกลง log
- **Secondary Categories:**
  - **Application Access Control & ID-Based Authorization Risk:** การอ้างอิงออบเจกต์ด้วย `id` ใน URL ทำให้ความแข็งแรงของการตรวจสิทธิ์ระดับออบเจกต์เป็นประเด็นที่ต้องยืนยัน
  - **Data Exposure/Privacy Risk:** เกี่ยวข้องกับข้อมูลส่วนบุคคลของบุคลากร

## หลักฐาน

### E-01 – RepSlip.aspx: GET พร้อมพารามิเตอร์ระบุตัวตนทุก request

**Source:** `result_v3.txt` หัวข้อ C (สรุปจาก `u_ex251119.log` – `u_ex251128.log`, ฟิลด์ `cs-method`, `cs-uri-query`)
**Timestamp:** 2025-11-19 – 2025-11-28

**Observed Facts:**
- `/webname/Main/MIS/Staff/Applications/RepSlip.aspx` พบ 85 request ทั้งหมดเป็น GET ที่มี query (GET-with-query = 85)
- ชื่อพารามิเตอร์ที่พบ: `id`, `periodid`, `salarytype` (85 request)
- status: 200 จำนวน 82 ครั้ง, 500 จำนวน 3 ครั้ง
- จากภายนอก (EXT) 27 request, 13 IP, 11 ผู้ใช้

**Security Interpretations:**
- สอดคล้องกับการส่งตัวระบุผู้ใช้และงวดเงินเดือนผ่าน URL
- ยังไม่ทราบว่า `id` คือรหัสพนักงานหรือรหัสภายในแอป และ log ที่ได้รับไม่แสดงค่า query จึงไม่ยืนยันความอ่อนไหวของค่าจริง

### E-02 – หน้าบุคลากร/เงินเดือนอื่นที่ใช้ GET พร้อม `id`

**Source:** `result_v3.txt` หัวข้อ C
**Timestamp:** 2025-11-19 – 2025-11-28

**Observed Facts:**
- `StaffSalary.aspx` 83 request (GET-with-query 76, พารามิเตอร์ `id`)
- `StaffInfo.aspx` 37 request (GET-with-query 37, พารามิเตอร์ `id`)
- `Web025_1.aspx` 56 request (GET-with-query 28, พารามิเตอร์ `id`)
- `StaffAttRequestData.aspx` 412 request (GET-with-query 222; ชุดพารามิเตอร์ `attleavetype, id, requesttype, requestyear` 237 request)

**Security Interpretations:**
- รูปแบบเดียวกันปรากฏหลายหน้า แสดงว่าเป็นแนวทางของแอป ไม่ใช่จุดเดียว
- ยังไม่ทราบว่าหน้าเหล่านี้รองรับ POST ได้หรือไม่

### E-03 – ฟิลด์ Referer พก query (id) ของหน้าก่อนหน้ามาด้วย และไม่พบการไล่ค่า id

**Source:** `u_ex251119.log` – `u_ex251128.log` (ฟิลด์ `cs(Referer)`), `result_v2.txt` (หัวข้อ ID PARAM), `README.txt` (รายการฟิลด์)
**Timestamp:** 2025-11-19 – 2025-11-28

**Observed Facts:**
- ใน request ของ `RepSlip.aspx` ทั้ง 85 ครั้ง ฟิลด์ `cs(Referer)` มี query string (พารามิเตอร์ `id`) ติดมา โดย 83 ครั้งมาจาก `StaffSalary.aspx` และ 2 ครั้งมาจาก `StaffInfo.aspx`
- ทั้งชุด log มี Referer ที่มี `?` จำนวน 5,904 จาก 18,592 รายการที่มี Referer (ประมาณ 32%)
- ไม่มี (IP, หน้า) ใดที่ใช้ `id=` ต่างกันตั้งแต่ 10 ค่า (หัวข้อ ID PARAM ว่าง)

**Security Interpretations:**
- ตัวระบุจึงปรากฏซ้ำสองที่ใน log (`cs-uri-query` และ `cs(Referer)`) เพิ่มพื้นผิวการรั่วไหลผ่านการเก็บ log
- Referer ที่พบเป็นการอ้างอิงภายในระบบเดียวกัน จึงยังไม่พบหลักฐานว่า query รั่วไปยังเว็บภายนอก
- ไม่พบรูปแบบการไล่ค่า id ตามเกณฑ์ที่ใช้ แต่เกณฑ์เป็นเพียงตัวตรวจหนึ่งตัว และไม่ได้ยืนยันว่า id เดาไม่ได้

## การวิเคราะห์ช่องโหว่และความเสี่ยง

1. **Sensitive Identifiers in URL Query String:**
   - **Evidence:** E-01, E-02
   - **Analysis:** ตัวระบุงวดเงินเดือนและผู้ใช้ถูกส่งผ่าน GET ในหลายหน้า ทำให้ถูกบันทึกใน `cs-uri-query`
   - **Potential Impact:** ผู้ที่เข้าถึง log, proxy หรือ browser history อาจเห็นตัวระบุและนำไปทดลองเรียกหน้าอื่น
   - **Limitation:** ไม่เห็นค่าจริงของ query และไม่ทราบว่า id เดาได้ง่ายเพียงใด

2. **Object-Level Authorization Dependence:**
   - **Evidence:** E-01, E-03
   - **Analysis:** เมื่อใช้ `id` ใน URL ความปลอดภัยพึ่งพาการตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ ซึ่งยังไม่มีหลักฐานเชิงบวกหรือลบ
   - **Potential Impact:** หากตรวจสิทธิ์ไม่ครบ ผู้ใช้อาจเรียกข้อมูลของผู้อื่นได้
   - **Limitation:** ไม่พบการไล่ id และไม่มี response body จึงยืนยันผลไม่ได้

## ข้อแนะนำ

### Immediate / Short-term (Quick Win)

1. **ปิดการบันทึกหรือปกปิด query string ของหน้าเงินเดือน/บุคลากรใน log**
   - **Priority:** High
   - **Owner:** Infrastructure / IIS Admin
   - **Estimated Effort:** Low
   - **Verification:** ตรวจตัวอย่าง log ว่า `cs-uri-query` ของ `/MIS/Staff/*` ไม่มีค่า id
2. **ตั้ง Referrer-Policy (`no-referrer` หรือ `strict-origin-when-cross-origin`)**
   - **Priority:** Medium
   - **Owner:** Infrastructure / Application Development
   - **Estimated Effort:** Low
   - **Verification:** ตรวจ response header ของหน้าที่เกี่ยวข้อง
3. **จำกัดสิทธิ์เข้าถึงและระยะเก็บ log ที่มีตัวระบุ**
   - **Priority:** Medium
   - **Owner:** Infrastructure / Security
   - **Estimated Effort:** Low
   - **Verification:** ทบทวนรายชื่อผู้มีสิทธิ์อ่าน log และนโยบายเก็บรักษา

### Long-term / Architectural Fix

1. **ย้ายการส่งข้อมูลระบุตัวตนไป POST หรือใช้ตัวระบุแบบ opaque และตรวจสิทธิ์ระดับออบเจกต์ฝั่งเซิร์ฟเวอร์ทุกครั้ง**
   - **Priority:** High
   - **Owner:** Application Development Team
   - **Estimated Effort:** High
   - **Verification:** ทดสอบเจาะระบบ (IDOR) ว่าการแก้ id ไม่ให้ข้อมูลผู้อื่น และ log ไม่มีตัวระบุ
